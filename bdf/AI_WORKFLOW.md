# AI Workflow

> The framework workflow for AI coding agents.

---

# Purpose

This document defines the workflow every AI coding agent follows when working with the Builder Development Framework.

The framework is designed so that future AI agents understand the workflow automatically.

An agent that follows this workflow produces complete changes:

- Implementation.
- Architecture.
- Documentation.
- Templates.
- Tests.
- Version records.
- Release.

---

# Master Workflow

Every framework task follows the same workflow.

```
Read Blueprint

↓

Read Project Adapter

↓

Read Current Version

↓

Read Requested Improvements

↓

Determine Impact

↓

Update Architecture

↓

Update Documentation

↓

Update Templates

↓

Update Builder

↓

Update Tests

↓

Update Version

↓

Generate Release
```

No stage may be skipped.

The order is fixed.

---

# Stage Definitions

## Read Blueprint

Read:

```
FRAMEWORK.md
```

Understand the generic engineering process.

Also read the component documents relevant to the task.

## Read Project Adapter

Read:

```
ADAPTER.md
```

of the project.

Understand the project-specific facts.

## Read Current Version

Read the project version file.

Understand the current state.

## Read Requested Improvements

Read the user's requested improvements.

The user describes the desired behavior only.

## Determine Impact

Perform the impact analysis defined by the Blueprint Engine.

Determine:

- Which architecture documentation changes.
- Which builder stages change.
- Which documentation changes.
- Which templates change.
- Which tests change.
- Which version records change.

## Update Architecture

If the change alters how components connect, the architecture documentation changes first.

Architecture changes are documented before implementation.

## Update Documentation

Update every affected document.

Documentation and implementation ship together.

## Update Templates

Update every affected template.

A template change is a framework change.

## Update Builder

Modify the implementation.

## Update Tests

Add or modify tests.

Verify existing tests still pass.

## Update Version

Update the version files and changelog.

Move completed work from the roadmap to the changelog.

## Generate Release

Produce the release.

Releases are generated by the project's release manager from the release registry: the AI records the release facts, the user reviews them, and the release manager generates all version documentation.

# Agent Rules

## Rule 1 — Understand Before Changing

No file is modified before the framework and the adapter are understood.

## Rule 2 — Complete Changes Only

A change is complete when every stage of the master workflow is finished.

A code-only change is a defect.

## Rule 3 — Never Guess

When documentation and implementation disagree, the agent:

1. Does not guess.
2. Identifies the inconsistency.
3. Asks for clarification.

Consistency is more important than speed.

## Rule 4 — Preserve the Architecture

The agent extends existing systems instead of replacing them.

The smallest reasonable change is made.

## Rule 5 — Respect the Source of Truth

Generated files are never edited manually.

Source files are the only authority.

## Rule 6 — Update the Session Records

At session start and end, the agent follows the session workflow of the project.

# Workflow Guarantees

When the master workflow is followed:

- No documentation falls behind implementation.
- No version record misses a change.
- No test suite ignores changed behavior.
- Every change is understandable by future agents.

---

## Unique Adapter Read Order and Gate-Aware Status Checks (Framework 2.3.0)

Before editing an adapter namespace or its implementation:

1. Read the target's five adapter documents under `adapters/<agent>/` when they
   exist, plus the governing research plan and gate reports.
2. Check the adapter lifecycle status before claiming or changing behavior.
   Fixture evidence, integration evidence, and live evidence authorize
   different claims; never use a stronger phrase than the evidence gate allows.
3. When a unique adapter drives an adaptive interface, consume the central
   capability contract; do not invent per-agent checks in pages.
4. Keep generic framework documents and templates free of target-specific
   paths, setting names, environment variables, versions, and support claims.
